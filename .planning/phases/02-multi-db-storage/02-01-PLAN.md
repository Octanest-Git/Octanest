<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `DATABASE_URL` / `OCTANEST_DB_DIALECT` env → `octanest-db` | Operator-supplied connection string containing credentials |
| `octanest-db` → Postgres / MySQL / SQLite server or file | SQL text and bound parameters cross into the engine |
| Host filesystem `./var` → SQLite file | Process creates directories and a database file on the host |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information disclosure | connect/migrate error strings | mitigate | `redact_url()` strips the password component; every `Err(String)` returned from connect/migrate/probe passes through it; unit test asserts a known password never appears in the error text |
| T-02-02 | Tampering | per-dialect migration drift | mitigate | `migration_parity` unit test asserts identical filename sets across `migrations/{postgres,mysql,sqlite}` — a migration added to one dialect only fails the build |
| T-02-03 | Tampering | SQL injection into probe statements | mitigate | Probe SQL is a fixed string per dialect with only bound placeholders (`$1` / `?` / `?1`); no `format!()` of any caller-supplied value into SQL |
| T-02-04 | Information disclosure | SQLite file on host disk | accept | `./var/octanest.db` inherits process umask; Phase 2 documents `var/` as runtime state and gitignores it (plan 02-03); filesystem hardening is an ops concern, no secrets stored in Phase 2 schema |
| T-02-05 | Denial of service | connection pool exhaustion | mitigate | `max_connections(5)` on Postgres/MySQL pools, `max_connections(1)` on SQLite (single-writer); no unbounded pool growth |
</threat_model>
